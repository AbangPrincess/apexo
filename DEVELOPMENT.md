# Apexo - development notes
Activity tracking + live circles + theft guard for bikes, motorbikes and cars. Flutter (Dart). Full scope is in SPEC.md. Read only the sections you need: `grep -n '^## ' SPEC.md`.

## Working rules
- Read only files you will edit. Batch edits. Max 250 lines per file; split big widgets into their own files. Comment only non-obvious logic.
- Add packages with `flutter pub add <pkg>` (never hand-edit versions), and only in the phase that first uses them. No code generators (build_runner, freezed, json_serializable, riverpod_generator): hand-write models with fromMap/toMap.
- Verify with `flutter analyze` and `flutter test` (piped to `| tail -n 25`).
- Format only the files you touched, at 100 columns: `dart format -l 100 <files>`. The default 80 columns reflows the whole codebase.
- Blocked on something only the owner can do (Firebase project, keys)? Use the demo backend, keep going, and list it under "Needs you" in README.md.
- Never commit passwords, keys, keystores or .env files. Never log or persist anything sensitive on the client (web localStorage and the console are visible in the browser's Inspect tools).
- Commits: short messages ("first commit", "second commit", ...), and only when the owner asks. Never push unasked.

## Conventions
- Material 3, provider + ChangeNotifier. Repository interfaces in lib/data with FakeRepository (demo, in-memory) and FirebaseRepository (lib/data/firebase). `createRepository()` picks Firebase when `DefaultFirebaseOptions.currentPlatform` returns options (the committed placeholder throws, so it falls back to the demo); `--dart-define=APEXO_DEMO=true` forces the demo. Never add the google-services Gradle plugin by hand.
- Layout: lib/core (theme, geo, units, weather logic), lib/data, lib/features/{auth,feed,record,circle,guard,alerts,me}, lib/widgets. Pure logic in lib/core with tests in test/.
- Responsive and adaptive: phones (Android + iPhone) get the bottom bar; >= 600 px (tablets, web) get a side rail and width-capped content. Respect safe areas; use adaptive widgets (Switch.adaptive, showAdaptiveDialog) so iPhone feels native.
- Original UI and copy only. Do not copy other apps' names, logos or assets.

## Decisions
- iOS is scaffolded (`--platforms android,ios,web`) and every screen is designed for iPhone too; building and signing it needs a Mac with Xcode. This overrides "iOS is not configured" in SPEC G1/G6.
- Packages are added in the phase that first uses them (P1: provider, shared_preferences, flutter_map, latlong2) so Android builds never break on unused native plugins.
- lib/core uses its own `GeoPoint` (pure Dart); conversion to latlong2 happens only inside `MapView`.
- Tabs are built lazily (first visit), so the map and its tiles load only when Circle is opened.
- Units and default activity live on the user profile (synced) and are cached in shared_preferences so the UI starts with them. Only these two settings (and, since P6b, an "onboarding seen" flag) are stored locally; no email, password or location is persisted on the device.
- Demo mode is in-memory: new accounts and changes reset on reload. The demo password check never logs or persists anything.
- Demo alert: John's 50 m boundary uses the real `GeofenceWatch`; the alert fires after 2 consecutive outside fixes (~20 s after sign-in) and, in the demo only, once per session so later laps stay quiet.
- Demo invite code TRAIL7 is kept as specified even though it contains I and L; generated codes (P4) exclude look-alikes and joining normalizes case and spaces.
- Password minimum is 8 characters (Firebase only enforces 6).
- P2: new passwords need 8+ characters with a letter and a number (live checklist on sign-up).
- P2: sign-up uses verify-after-create (the Firebase model): the account is created, a link is emailed, and the app stays on "Check your email" until it is verified. P6 Firestore rules must also require `request.auth.token.email_verified`. A code-by-email flow would need Cloud Functions (paid plan).
- P2: demo mode cannot send real email, so the demo backend keeps an outbox shown in a clearly labelled "Demo inbox". Links work once, a resend expires older links, and resends have a 60 s cooldown.
- P2: sign-in lockout lives in the backend (FakeAuth in demo; Firebase's own limits in P6, plus the same LoginThrottle client-side). 5 failures lock that email for 30 s, doubling up to 15 min. Unknown emails fail and lock the same way, and reset requests never reveal whether an email has an account.
- P2: profile photos are resized on the device (avatar 512 px, cover 1600 px), checked by their bytes (JPEG/PNG/WebP only, size caps), stripped of GPS EXIF tags, and stored as small data URIs on the profile. This works on the free Firebase plan, where Cloud Storage now needs the paid plan.
- P2: settings moved from the Me tab to a Settings screen (gear icon); Me is now a social-style profile with cover, photo, details, achievements, weekly chart and totals.
- P2: recording uses `package:clock` time so tests can fake it. The demo backend defaults to simulated GPS (switchable) so recording can be tried at a desk.
- P2: Android permissions for location, foreground service, wake lock and notifications are declared now (recording needs them); a short explanation dialog appears before the system permission request. Full rationale screens and the notification permission request remain in P6.
- P3: weather comes from Open-Meteo through `OpenMeteoSource` (injectable `http.Client`; tests pass a fake `WeatherSource`). `current` and `hourly` also ask for `is_day`, so night hours rank lower and riders get a lights reminder after dark.
- P3: hourly times are parsed as UTC instants using `utc_offset_seconds`; labels use the forecast location's clock, not the device's.
- P3: `rideVerdict` uses the spec thresholds for cycling and motorcycling, plus thunderstorms (avoid) and rain falling now (caution). Driving is capped at Caution, and heat is ignored for driving. The worst factor sets the verdict and its reason.
- P3: "Best time to ride" ranks the next 12 h by verdict, then a discomfort score (rain, wind, heat, night), then earliest.
- P3: the 15-minute cache is in memory only; nothing about weather or location reaches shared_preferences or localStorage. Offline keeps the last result ("Offline · Updated X min ago"); a cold start offline shows a Retry card.
- P3: weather uses the device position only when location access is already granted (it never asks for it) and sends it rounded to 0.01 deg; demo mode and denied access use Koronadal City (6.50, 124.85).
- P3: each new activity stores a `WeatherSnapshot` for its start: current values when fetched within 30 min of the start, else that hour's forecast. Starting a recording refreshes a stale cache.
- P3: on Record, the weather call replaces the all-zero stats card before a ride (live stats still appear once recording starts), so START stays within thumb reach. Screens under 900 px tall fold the hourly strip behind an "Hourly" toggle.
- Rename: the app was renamed from PedalTrack to Apexo (2026-11-03). Dart package `apexo`, Android `applicationId`/namespace and iOS bundle ID `io.github.abangprincess.apexo` (a namespace the owner controls; it is permanent once published to a store, so change it before the first release if a domain is bought). Demo email is `demo@example.com` (reserved domain).
- Colors: the six Apexo brand colors are in `Palette`; screens only use the roles in `AppColors` (see SPEC G3 and README "Design"). Red is reserved for brand, START and alerts; primary buttons are ink; input focus is ink so it never looks like an error. `AppColors.on(color)` picks ink or white text for solid fills.
- P4: circle operations live in `FakeCircles` (lib/data/fake/fake_circles.dart), written like the P6 Firestore client: a user writes only their own uid and member doc; the owner may also remove members. Limit: `maxCirclesPerUser` = 3, enforced in the backend and checked in the UI.
- P4: invite codes use `inviteAlphabet` (no 0/O/1/I/L) from `Random.secure()` and are retried until unique. P6 needs an `inviteCodes/{code}` lookup doc readable by signed-in users, because circle docs are readable only by members. P6 should also rate-limit lookups.
- P4: joining and creating always pass the consent screen. Both choices complete the action; only "share" turns sharing on. If location access is refused, the circle is still joined, with sharing paused.
- P4: one sharing switch per circle (the member doc's `sharing` field, synced). The device location stream runs while any circle is shared. While recording, the recording's fixes are reused, so only one GPS stream runs. Demo (simulated GPS) shares a parked spot until a recording starts.
- P4: `ShareGate` enforces the G4 write budget: at most one write per 5 s, only after 10 m, plus a 60 s heartbeat when still. A status change skips the distance check but not the 5 s floor.
- P4: pausing writes position 0,0 so members cannot read where you paused. `Member.onMap` (sharing and a real position) decides who gets a pin. A new member has no pin until their first fix.
- P4: a persistent "Sharing live" bar shows on every tab while sharing; Android also shows the geolocator "Sharing location" foreground notification. The sharing state is not persisted on the device; it comes back from the member docs at sign-in.
- P4: the owner leaving passes ownership to the next member; the last member leaving deletes the circle and its members, alerts and feed.
- P4: "Circles" activities are copied to `circles/{cid}/feed/{aid}` in every circle of the owner (client fan-out, no Cloud Functions). The copy drops the vehicle link and thins the path to 25 m. Joining backfills your 20 latest; leaving or removal deletes your entries. Others' activities open read-only (no delete).
- P4: packages share_plus (invite sharing; copies to the clipboard where sharing fails) and battery_plus (member battery; null where unsupported).
- P4: create/join flows clear any open snackbar so it never covers their buttons; consent buttons are pinned at the bottom (thumb reach on small phones).
- P5: guard rules are pure Dart in lib/core/guard_logic.dart. `GeofenceWatch`: exit after 2 consecutive fixes outside radius + accuracy, once per exit, re-armed after 2 consecutive fixes back inside (the spec says "after re-entry"; 2 fixes stops edge jitter re-arming it). `BatteryWatch`: low battery once at 15 %, re-armed above 20 %. `NudgeDetector`: 3 jolts above the sensitivity threshold within 2 s, then quiet for 5 min.
- P5: only leaving the boundary marks the vehicle stolen and turns the ring red. A nudge or low battery is a warning alert only, because a bump should not declare a theft.
- P5: the active vehicle is `users/{uid}.activeVehicleId` (empty means the first). `VehiclesController` keeps my pin's vehicle in step in every circle and writes only when it differs. Switching vehicles and deleting a guarded one are blocked while armed.
- P5: one alert event is written to every circle I am in under the same id. `AlertsController` watches all circles, shows each event once, merges acks, and only counts alerts from others that arrive after a circle's first load as "incoming". While the vehicle is missing, the owner's phone moves the alert along (`follow`, throttled by `ShareGate`), so View on map and Navigate lead to where it is now. Updates start from each circle's own copy so acks are kept. P6 should use field-level updates for alerts and member docs, so concurrent writers never overwrite each other.
- P5: incoming theft alerts show a dialog (View on map, Navigate, It's me = ack) plus a system notification with sound (flutter_local_notifications, channel "Theft alerts", iOS time-sensitive); low battery shows a snackbar. Notification permission is asked on ARM and from a card in Alerts, never unasked. On the web nothing is set up (no service worker) until the person turns it on.
- P5: guard mode does not auto-resume. If the backend says guarded but this phone is not watching, the Guard screen offers "Watch from this phone" or "Disarm", because auto-resuming on a second phone would alarm at once.
- P5: guard uses its own low-rate location stream with the Android "Guard mode on" notification and no iOS auto-pause. The demo vehicle stays parked; "Test the alarm (demo)" feeds two fixes outside the boundary.
- P5: packages flutter_local_notifications (Android needs core library desugaring, now in build.gradle.kts; iOS AppDelegate sets the notification delegate), sensors_plus (user accelerometer at the normal rate) and url_launcher (Navigate opens https://www.google.com/maps/dir/?api=1&destination=LAT,LNG; Android manifest queries https).
- P5: CircleController no longer holds alerts; it keeps the active circle, members and a pending map focus for "View on map".
- Backend (decided 2026-11-04): stay on Firebase Spark (Auth + Firestore) as specified. With uncertain usage, it wins on never pausing (Supabase's free tier pauses after a week without activity), needing no card and no email-service setup, and having offline sync built in; the daily write limits only matter with many users, and `ShareGate` keeps writes low. Push while the app is closed stays a known limit. If real users arrive, turn on Blaze for one Cloud Function (alert push) and move live positions to the Realtime Database.
- P6 split: dark theme touches 54 files (colors are `AppColors` constants), so polish moved to P6b; P6 is the Firebase backend, rules and deploy.
- P6: `FirebaseRepository` is built from mixins like the fake (fb_auth, fb_profile, fb_circles, fb_alerts) and is tested against fake_cloud_firestore and firebase_auth_mocks (dev only). The rules are not emulator-tested yet: firebase-tools needs Java 21+ (this machine has 20).
- P6: until the email is verified the profile comes from Auth alone, because every rule requires `email_verified`; the first verified sign-in creates users/{uid}. `reloadUser` refreshes the ID token so the rules see the new claim. Client-side `LoginThrottle` mirrors the demo lockout on top of Firebase's own limits.
- P6: inviteCodes/{code} {circleId, name, ownerName, memberCount} is readable by exact code only (no listing); it is how non-members find a circle, since circle docs are members-only. Joining adds only your own uid (rules check the set difference); leaving removes only you and a leaving owner hands over to a member; the owner removes one member at a time; the last one out deletes the circle, its alerts and the code.
- P6: member docs and alerts are updated field by field (`changedFields` against the last snapshot), so sharing, guard and vehicle writes never overwrite each other. A write to a removed member's doc fails quietly instead of recreating it.
- P6: writes wait at most 4 s for the server (`settle`); offline, Firestore keeps them in the local cache and syncs later, so the UI never hangs.
- P6: feed copies are keyed `<ownerUid>_<activityId>` with an `activityId` field. The backfill reads the 50 newest activities and keeps "Circles" ones client-side, so no composite index is needed (no firestore.indexes.json).
- P6: web keeps nothing on disk (Firestore cache off, Auth persistence SESSION), in line with the Inspect-surface rule; phones keep Firestore's offline cache and stay signed in.
- P6: the real `lib/firebase_options.dart` stays out of Git with `git update-index --skip-worktree`; google-services files and .firebaserc are ignored. The Pages build is always the demo (`APEXO_DEMO`), analyzes and tests first, and uses Flutter 3.38.7.
- P6: a profile with both photos at their caps is ~960 KB of base64, just under Firestore's 1 MiB doc limit. If photo caps grow, move photos to their own docs.
- P6: firebase-auth's Android SDK is compiled with Kotlin 2.4 metadata, so the Kotlin Gradle plugin moved from 2.2.20 to 2.3.21 (android/settings.gradle.kts) and `kotlinOptions.jvmTarget` became the `kotlin { compilerOptions }` block. Debug APK and the Pages web build both pass. Locally in Git Bash, prefix web builds with `MSYS_NO_PATHCONV=1` or the base href turns into a Windows path.
- P6b dark theme: follows the system setting. Brand and signal colors are constants; the neutral roles (`ink`, `onInk`, `text`, `textMuted`, `surface`, `surfaceAlt`, `hairline`, `accentSoft`, `dark`) are getters backed by `Neutrals.day` / `Neutrals.night` (lib/core/theme.dart); `AppTheme` (lib/core/app_theme.dart) builds both ThemeData from them. `PaletteSync` (MaterialApp builder) switches the roles and, on a runtime change, rebuilds the tree in place with `reassembleApplication()` so tabs, scroll and maps keep their state. Put text on ink fills in `onInk`, dark marks on volt/orange with `AppColors.on()`, and dots or outlines drawn on map tiles (always light) in `mapInk`.
- P6b dark theme: small red text on asphalt is below 4.5:1, so in dark mode the selected tab's label is light and only its icon stays red; text buttons use light ink. OSM tiles stay light.
- P6b permissions: every system request is preceded by a sheet saying why (`explainPermission` / `explainLocationIfNeeded`): recording, sharing, locate-me, guard mode (location, then notifications). The join and create consent screens already explain sharing. Saying "Not now" to notifications still arms guard mode. The camera option says it is for one photo. No background-location permission is requested; the foreground services cover a locked screen.
- P6b onboarding: 3 slides (record, circles, guard) once per device before sign-in, with Skip; the "seen" flag is the third and last value kept in shared_preferences.
- P6b errors and offline: Home and Circle show "Couldn't load ... Try again" when their listener fails; other listeners keep their last data (`_keepLast`). An offline bar (connectivity_plus) shows on every tab; saved data keeps working from Firestore's cache on phones.
- P6b accessibility: test/accessibility_test.dart runs Flutter's tap-target (48 dp), labelled-tap-target and WCAG text-contrast guidelines on every tab in light and dark, and every tab at 2x text on two phone sizes. Fixed: rows that could not shrink (sign-in divider, weekly header, weather wind, achievements count) and the round record buttons (label scales down inside the circle).
- P6b icon: the brand mark (white chevron, volt apex dot, Apex Red) drawn by a PowerShell System.Drawing script for Android mipmaps, iOS AppIcon (opaque, no alpha, as the App Store requires) and web (rounded, maskable with the mark in the safe zone, 32 px favicon). Replace it with a designed icon before a store release.
- Firebase connected (2026-11-04): project `apexo-497f5`; apps registered with FlutterFire 1.4.1. The project's Firestore database is named `default` (Enterprise edition, asia-southeast1), not `(default)`; Enterprise supports the same mobile/web SDKs with live listeners and offline use, and the free tier covers one database per project, so the app uses it via `FirebaseFirestore.instanceFor(databaseId: firestoreDatabaseId)` (`--dart-define=APEXO_FIRESTORE_DB=...` for another project) and firebase.json deploys the rules to it (`releases/cloud.firestore/default`). Enterprise reads are billed per 4 KiB, so the profile doc's photos make each profile read cost more units; move photos to their own docs if reads get tight.
- FlutterFire 1.4.1 has no flag to skip its Gradle edits; they are reverted after `configure` (Dart-side options need no google-services plugin). The real `lib/firebase_options.dart` is `skip-worktree` on this machine; google-services.json stays ignored.
- Android test builds (2026-11-04): release builds are signed with an upload key (`android/app/upload-keystore.jks`, PKCS12, alias `upload`, password in `android/key.properties`); both are git-ignored and must be backed up privately. Without key.properties (CI, another computer) release builds fall back to the debug key. Builds go out through Firebase App Distribution to the group alias `testers`; 1.0.0 (1) went out 2026-11-04 and 1.0.1 (2) on 2026-11-05 (walkie-talkie, profiles, photo editor and the feedback rounds). Bump `version:` in pubspec.yaml for every new build.
- Real web app (2026-11-04): Firebase Hosting site `apexo-497f5` (https://apexo-497f5.web.app) serves `build/web` from a plain `flutter build web --release` (real backend; the GitHub Pages build stays demo). firebase.json has the hosting config (SPA rewrite; no-cache on every file, see "Hosting cache" below). `.firebase/` (deploy cache) is ignored. This is the iPhone route until there is a paid Apple account.
- Web build cache bug: a release web build without dart-defines reused an old `.dart_tool/flutter_build/<hash>/web_plugin_registrant.dart` from before Firebase was added, so the bundle had no Firebase web code and startup threw a pigeon "channel-error". Always `flutter clean` before a release web build that is deployed. The Flutter service worker caches the old bundle in browsers that saw a broken build; a new deploy replaces it on a later load.
- Tracking accuracy (2026-11-04, owner report: 0.02 km and 1 km/h while standing still). `RideTracker` no longer adds every fix: movement is judged over the last 8 s by comparing the average position of the older half of the window with the newer half (averaging cancels GPS scatter), and counts only when that beats `max(type.minStepM, accuracy)` at `type.minMovingKmh` or faster (cycling 3, running 2.5, motorbike and car 5 km/h). Starting needs two moving judgements in a row. Recording starts in autoPaused ("GPS ready · start moving") and the moving-time clock runs only while moving: it freezes at the last moving fix and auto-pauses after 5 s still. Path points are at least `max(minStepM, accuracy/2)` apart. Tests cover indoor-style scatter with and without a reported speed.
- Running (covers jogging; one type, the pace tells them apart): `ActivityType.running` with speed cap 9 m/s; runs show pace (min/km or min/mi, `formatPace`) instead of speed on Record, cards and detail. The weather call treats wind as a nuisance on foot and says "run". firestore.rules accept 'running'.
- Record while live: a map that follows the phone and fills nearly the whole phone screen (keeps the chosen zoom; panning stops following until re-center, now top right), with the route, the position dot and an accuracy ring. PAUSE, RESUME and FINISH (72 px) float at the bottom of the map; the four stats are one slim strip below (`RecordStats(oneRow: true)`; long figures shrink to fit). Wide screens keep the 2x2 and the controls beside the map. `RecordController.position` is the live fix, also while still; location sharing during a recording uses it.
- Font (2026-11-05, owner: "like Facebook", not Android-like): Inter (SIL OFL, assets/fonts with OFL.txt, static 400/500/600/700 from the official rsms/inter 4.1 release), bundled so nothing is fetched at runtime; it has tabular figures. The iPhone app (not the web) uses the system font, San Francisco, which Apple doesn't license for bundling. iOS-style sizes (body 17, subhead 15, footnote 13) and tracking (0 or slightly negative instead of Material's wide letter spacing); titles w700, labels w600/w500, body w400. Barlow was dropped. The four files add about 1.6 MB to the first web load; the service worker caches them after that.
- Weather icons are painted line art (`WeatherArt`, lib/widgets/weather_art.dart; owner asked for outline only, two colors): one stroke color (`AppColors.text`, so black on light and white on dark) on the background, no fills and no color roles. Sun, crescent moon, clouds, rain, drizzle, snowflakes, bolt, fog. A cloud (or the bolt) in front erases what is behind it plus a thin gap (layer + `BlendMode.clear`), like iOS weather symbols. `WeatherGlyph` has no backdrop circle any more, and the hourly rain drop is an outline too.
- Splash: web/index.html shows the mark (no name) at once and fades it on Flutter's `flutter-first-frame` event; the in-app loading screen shows the same 96 px mark; Android before 12 has it on the launch layer (12+ uses the app icon); iOS LaunchImage is the mark.
- Achievement tiles reserve two title lines (scaled with text size) and always show the bar (full volt when earned), so every tile is the same height.
- Greetings are title case ("Good Evening").

- Side menu (tablet and web): tap the Apexo mark to fold the rail to icons only (tooltips on the icons, labels kept for screen readers) and again to open it. It starts open from `Breakpoints.large`; the choice lasts for the session (not stored). The wide mark and Record button appear only once the rail has finished opening (`NavigationRail.extendedAnimation`), so nothing overflows mid-animation. Folded rails no longer show labels under the icons.
- Maps (2026-11-05): Google Maps would cost nothing at this size (phone SDKs unlimited, web 10,000 loads a month free, then $7 per 1,000) but Google needs a billing account with a card, and linking one to apexo-497f5 would move Firebase to Blaze. The owner chose to stay on the free OpenStreetMap tiles; if that changes, use a separate Google Cloud project for the Maps key.
- Walkie-talkie (2026-11-05): push-to-talk voice messages per circle, not a live call (a live intercom needs a paid voice server). Hold the Talk button and let go to send, or tap, talk, tap again; 30 s limit (`maxVoiceLength`), auto-sent. Others' new messages play by themselves on any tab, one after another (auto-play switch); every message can be replayed for 24 h (`voiceKeepFor`), and the sender's app deletes its expired ones. Talk floats on the Circle map (bottom left) and on the live ride map, so riders never switch tabs; the message list sits under the members. Storage: Cloud Storage needs Blaze since 2024, so audio lives in Firestore: `circles/{cid}/voice/{id}` (who, length, type, server time; watched, newest 30) and `circles/{cid}/voiceAudio/{id}` (bytes, read only when played, at most 400 KB by rule). Mono AAC 24 kbit/s 16 kHz (about 3 KB/s, a 10 s message is about 30 KB; Opus/WebM where a browser can't record AAC). Enterprise bills writes per KiB, so a 10 s message is about 30 write units plus about 8 read units per listener: fine for a few riders on Spark. Needs a connection (offline, phones queue the send); true offline radio between phones isn't possible across Android, iPhone and the web. Browsers can block auto-play until the page has been tapped once: the message then says "Tap it to play". Packages: record (all platforms), just_audio (phones play from a temp file, the web from a data: URI). Android RECORD_AUDIO, iOS NSMicrophoneUsageDescription, and a microphone explanation sheet before the first use.
- Circle profiles (2026-11-05): circle members can open each other's profile (tap a member's photo, or long-press the row; tapping the row still centers the map). Each member writes their own copy to `circles/{cid}/profiles/{uid}` (name, bio, hometown, photo, cover; never the email). The member doc's `profileRev` (FNV-1a of those fields) says which version is published, so `CircleController` republishes only after a change (and backfills circles joined before this), not every session: a copy with photos is up to about 1 MB of writes.
- Photo editor (2026-11-05): after picking, the person places the photo: a circle for the profile photo, a 3:1 frame for the cover (like X), drag to move, pinch, slider or mouse wheel to zoom. `lib/core/photo_crop.dart` (image package) turns the photo upright, crops and saves a JPEG with no metadata: profile 400x400, cover 1500x500, quality lowered until it fits the existing limits. Covers show 3:1 everywhere (`coverHeightFor`); the Me avatar is a little smaller to match.
- Verification email (2026-11-05, owner: it lands in spam and people miss it): Firebase only lets the password-reset email's text be edited, so the verification email can't carry a logo or new wording; sender name, reply-to and subject can be changed in Authentication > Templates. The emails come from noreply@apexo-497f5.firebaseapp.com, a shared Firebase address that mail services often file as spam. The fix that works is a custom domain for the emails (Templates > Customize domain, then the TXT and CNAME records Firebase gives); that needs a domain (about $10 to $15 a year). Meanwhile the verify screen tells people where to look first (Spam, Junk, Gmail Promotions, search "Apexo") and to mark it Not spam.
- Locked screen (2026-11-05, owner: recording must not stop until Pause or Finish): nothing ends a ride except Finish (and signing out). The phone apps record with the screen locked: Android runs the GPS stream as a foreground service with the "Recording ride" notification and a wake lock; iOS has UIBackgroundModes location and showBackgroundLocationIndicator. A web page can't: Safari stops it when the iPhone locks. So while a ride is live, the web asks for a Screen Wake Lock (`lib/core/screen_awake_web.dart`, Safari 16.4+, re-asked whenever the page shows again) so the phone doesn't lock by itself, and if the page was hidden for 20 s or more `RecordController` says how long nothing was recorded (an `AppLifecycleListener`, web only). The route then joins up in a straight line.
